# H01 — audit and expense recovery

Status: next-phase design draft. Implementation starts only after C01 is integrated into verified dev. User requested proceeding after the current reviewed PRs on 24 October 2026. This document does not authorize merging those PRs or deploying.

## Scope and dependencies

Dependencies: integrated F01, E02 and C01. Preserve A03 session enforcement. Branch from the then-current checked dev; use Sol high, Matt Pocock sequential TDD and Ponytail. Keep the existing authenticated HTTP/PostgreSQL, rendered Angular and owned-browser seams.

Deliver an attributable expense history plus versioned soft delete and restore. Preserve currency and original split intent. Do not add payment correction, group recovery, invitations, retention purge or a generalized event engine.

## Contract to finalize against integrated C01

- Record accepted expense creation, replacement, deletion and restoration transactionally with actor, server timestamp, resource version, operation identity when supplied, and before/after financial snapshots. Failed authorization, validation or conflict writes neither history nor money.
- Existing expenses receive an explicitly imported baseline. Preserve known financial payer and dates; do not invent the historical recorder or edits that were never retained. Previously hard-deleted expenses cannot be recovered.
- Replace hard expense deletion with a deletion marker and version advance. Ordinary list/detail, activity and all per-currency financial projections exclude deleted expenses. Retain their shares and audit history.
- Add an authorized history view and explicit restore command with expected version. Apply group membership checks before resource disclosure; former financial participation never grants access. Reauthorize under the existing group financial write lock.
- Restoration must verify current participants and financial lifecycle constraints. Reject stale, unauthorized or unsafe restoration atomically with actionable feedback. Restore once; a repeated or conflicting command must not change balances twice.
- Preserve E02 immutable create receipts after edit/delete/restore. A create replay must never perform a restoration. Retain C01 denomination and minor-unit precision without conversion.
- Choose the smallest expense-specific revision storage and endpoint shapes after inspecting integrated DTOs and migration numbering. Do not reserve a migration number while prerequisite branches are unmerged.

## Acceptance sequence

1. One authenticated HTTP red/green case for attributable creation and replacement history.
2. Soft-delete excludes the expense from every financial consumer while preserving history.
3. Versioned restore reinstates the same currency/shares once; stale and inactive-participant attempts leave history and balances unchanged.
4. Real PostgreSQL delete/restore/edit races preserve versions, per-currency conservation and authorization.
5. Rendered history, delete and restore controls show actors, dates and actionable conflicts, with pending-write and account-switch isolation.
6. Rehearse a populated pre-H01 upgrade, then full required checks, separate Standards/Spec reviews, desktop/mobile browser acceptance and a PR to dev.

Production promotion and irreversible purge policy remain separate decisions. Finalize rollback restrictions before enabling soft deletion: old binaries must not count retained deleted rows as active financial data.
