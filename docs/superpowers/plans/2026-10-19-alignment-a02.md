## Behavior and interface

Recovery requests accept normalized email and return the same 202 with no token/account disclosure. Confirmation commands accept a 256-bit random URL-safe token; persistence retains only SHA-256, purpose, user, target email and expiry. Issuing replaces the prior same-purpose challenge. User-row serialization and token recheck make expiry, single use, concurrent consumption and cross-purpose rejection atomic. PostgreSQL owns final email uniqueness. No existing address becomes verified through migration or registration.

Public POST /api/auth/password-reset-requests {email}, /password-resets {token,password}, /email-verifications {token}, /email-change-confirmations {token}. Authenticated POST /api/me/email-verification-requests {}, /password {currentPassword,password}, /email-change-requests {currentPassword,email}. GET /api/me adds emailVerified. Password writes require 8+ characters and at most 72 UTF-8 bytes; current passwords are bounded before BCrypt. Changing email requires current password and confirmation at the replacement email (access to the old mailbox is not required); the old login remains until replacement confirmation.

Recovery/confirmation and sensitive authenticated commands consume process-local, bounded IP/account attempt budgets before lookup/BCrypt, preserving existing login/register policies. Tokens expire after 30 minutes; replacement and password changes invalidate outstanding account challenges. Invalid/expired/replayed token returns the same 400. Confirmation is an explicit POST, never automatic on GET.

Delivery uses Spring's standard JavaMailSender with provider-neutral SMTP, explicit enabled/from/frontend URL configuration and timeouts. Disabled/misconfigured transport returns sanitized 503 for all reset addresses. SMTP failures roll back challenge issuance; no raw credentials in responses or logs. Links put tokens in URL fragments, removed from browser history before explicit confirmation; no capture routes or development production fallbacks. Root will configure an owned local mailbox only. No real delivery/provider configuration is authorized.

Root selected bounded credential-version revocation: password reset/change and confirmed actual email change increment user credentialVersion atomically, and every protected JWT validates its version against current persisted state. Missing legacy version means zero, malformed/negative/unknown-user claims fail closed, and unchanged legacy accounts keep working. The UI logs out after successful password change; confirmation instructs login with the new identity. A03 retains device/session/refresh/logout-all lifecycle. Authentication already in flight at commit may finish; every subsequent validation rejects the superseded credential. Current-password verification + new mailbox confirmation permits a signed-in user to replace a lost mailbox safely.

## Rollout and verification

V13 adds email verification state, credential state if selected, and challenge storage; V1–V11 stay immutable. E02 V12 must precede V13 in promotion (or ship together). Existing users remain unverified. Keep additive columns/tables on binary rollback; old writers must not serve sensitive lifecycle commands. SMTP is disabled by default; deployment requires separately reviewed sender/HTTPS URL configuration and delivery rehearsal.
