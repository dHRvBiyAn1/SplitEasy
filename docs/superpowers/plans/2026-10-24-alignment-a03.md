## Accepted contract

- Every login/registration creates a persisted device session and returns the existing one-hour HS256 bearer response plus opaque `sessionId`. JWTs include `sid` and existing credentialVersion. Each protected request checks persisted account version AND matching active, unexpired session ownership. Revoke/logout commit stops all later requests on every instance; requests authenticated before commit may finish.
- Immediate cutover: reject all JWTs lacking a valid persisted `sid`. Never adopt a bearer token into a session. Existing users re-login once after rollout. This is necessary to avoid leaving legacy copied tokens outside selective revocation.
- `GET /api/me/sessions` lists only the caller's active sessions, created/last refreshed/absolute expiry, safe bounded device label, and `current`. No IP, refresh secret/hash, email or other accounts. `DELETE /api/me/sessions/{id}` idempotently revokes only an owned session; unknown/other-account identifiers return the same 204. `POST /api/me/sessions/logout-all` revokes all account sessions atomically. `POST /api/auth/logout` uses bearer session identity and revokes that session; it never clears a cookie, preventing delayed old logout responses from erasing a later login's cookie.
- Refresh continuity uses 256-bit random opaque credentials in host-only `__Host-spliteasy-refresh`, Path=/, Secure, HttpOnly, SameSite=Strict (frontend/API share the split-easy.io site). No refresh or access credentials are written to browser storage/URLs/logs. API JSON exposes only access credentials. Secure cookies remain mandatory; localhost is browser-supported for local HTTP development.
- `POST /api/auth/refresh` requires an exactly allowlisted Origin and `X-SplitEasy-Session: 1`, with credentialed exact-origin CORS. Login/register reject a supplied untrusted Origin before issuing cookies (login CSRF). Other existing bearer-only commands retain their existing policy. Missing Origin on refresh is rejected. Cookie alone never authenticates protected business requests.
- Sessions expire after 30 days absolute or 7 days idle; successful renewal is capped at 2048 rotations and the next attempt revokes the exhausted family. Access lifetime remains 3600 seconds, but server session expiry/revocation wins. Refresh rotates atomically under the existing account row lock. Only SHA-256 hashes are persisted; consumed hashes are retained until family expiry to detect any reuse, at most 2049 per session. Reuse revokes the complete session family and returns 401; concurrent duplicate refresh therefore fails closed, including the token issued to the first winner. Lost refresh response requires re-login (no replay grace or secret restoration).
- Browser auth operations/refresh use native Web Locks when available to serialize tabs. Other tabs receive only a nonsecret auth-change marker; they clear owned account state and renew from the cookie before private routes. Without Web Locks, strict duplicate detection may require re-login after a race; correctness still fails closed. Bootstrap refresh finishes before initial routing. Restored pending drafts are usable only when their immutable stored owner matches the successfully renewed identity; initial renewal does not reset them. Access credentials remain memory-only. Login/account-switch/refresh/logout responses are generation-owned so old callbacks cannot replace a newer identity; local logout resets owned state immediately and sends captured bearer credentials to the server; network failure reports that server revocation could not be confirmed. A stale protected 401 must never issue server logout against a newer session.
- Password reset/change and confirmed actual email change retain credentialVersion invalidation and atomically revoke persisted sessions; verification alone does not. Existing authentication/recovery rate limits and generic account-privacy responses remain unchanged. Refresh gets a small process-local IP limit using the existing limiter machinery; no retry loop.
- Revoked/expired session families and their hashes are deleted at login under the account lock; unknown old credentials still receive 401. No scheduler/dependency. At most 20 retained families, deleting oldest on overflow; each family has at most 2049 hashes. Inactive accounts retain expired rows until next login. Idle-expired sessions never revive.

## Migration and rollback

A03 owns only V14; C01 owns V15+. Merge/apply V14 before V15 or together; never enable Flyway out-of-order. Schema is additive, but hard-cutover session validation is a security behavior: an old binary accepts revoked/legacy bearer tokens. Prefer forward fix; reviewed rollback requires all-instance signing-key rotation and forced re-login. Keep V14 schema on rollback. Rolling mixed old/new binaries cannot provide immediate revocation and must not be presented as a supported release strategy. Production SMTP remains disabled and outside this task.
