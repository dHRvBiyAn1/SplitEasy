## Model

- A **contribution** is money one financial participant actually paid towards an expense. It is
  distinct from a **share** (what a participant owes). Both are integer minor units in the
  expense's immutable currency.
- Invariant per expense: `sum(contributions) = sum(shares) = amount`. Each contribution is
  positive and at most 1e12; one row per participant.
- `expenses.paid_by` stays, non-null, and now means the **primary payer**: a contributor the
  client names explicitly, who is the single rounding recipient (see below). For every
  single-payer expense it is the only contributor, so every existing reader of `paid_by` keeps
  its meaning.

## Migration and backfill (V23)

- New table `expense_contributions(id uuid PK, expense_id → expenses ON DELETE CASCADE,
  participant_id → participants, amount_cents bigint CHECK > 0)`, unique
  `uq_expense_contributions_expense_participant (expense_id, participant_id)` (leftmost prefix
  serves the expense FK), index `idx_expense_contributions_participant`.
- Backfill one row per existing expense, deleted ones included (so restore still works):
  `(paid_by, amount_cents)`. Flyway runs it once and the unique key rejects duplicates.
  Reconcile: row count = expense count, `sum(amount_cents)` equal, every contributor equals
  `paid_by`.
- No change to expenses, shares, split intent, versions, deletion markers, revision JSON or
  create-operation JSON. Old revision/receipt snapshots simply lack `contributions`.
- **Rollout:** drain old backends before V23. An old binary inserts expenses without contribution
  rows, and readers now sum paid amounts from contributions, so that expense's payer would vanish
  from balances. Rollback before any multi-payer write is schema-compatible (old code ignores the
  table). After a multi-payer write an old binary treats the primary payer as having paid
  everything — still zero-sum but wrong — so rollback is forward-fix only.

## Wire contract (backward compatible)

- `CreateExpenseRequest.contributions`: optional `[{userId, amountMinor}]`. Absent/null keeps the
  exact single-payer behaviour: `paidByUserId` paid the whole amount. Present: nonempty, unique
  active financial participants, each `1..1e12`, `BigInteger` sum equal to the amount,
  `paidByUserId` must be one of them. Invalid input is 400 before any row changes. `paidByUserId`
  stays required. Omitted from serialized intent when null, so pre-E03 keyed retries still match.
- `ExpenseResponse.contributions`: always present for current reads, `[{user, amountMinor,
  currency}]`, ordered like shares (display name). `paidBy` remains the primary payer.
- `ExpenseSummary.payerCount`: number of contributors, so a list can say "2 people paid" without
  a detail read. `viewerDeltaMinor` becomes the viewer's owned contributions minus owned shares.
- A **PUT without contributions on a multi-payer expense is 409** ("reload in an updated app"),
  mirroring C01's legacy-currency guard: an old client's full replace must not silently collapse
  several payers into one. PUT with contributions replaces both sides atomically.
- Keyed create replay: contributions sorted by `userId` are part of the intent; changed
  contributions on the same operation ID are 409.

## Net balances

Unchanged formula, new source for paid: `net = contributions − shares + paymentsMade −
paymentsReceived − refundReceived + refundAllocated`, one aggregate `GROUP BY` over
`expense_contributions` replacing the `paid_by` sum. Canonical owner mapping (G01) is applied
before summing, as today. Balances sum to zero per currency because contributions and shares
both sum to the amount.

## Deterministic pairwise attribution

Direct (unsimplified) obligations need who owes whom inside one expense. Splitwise's private
rule is not inferred. Ours, per expense:

1. Map contributions and shares to canonical owners and sum per owner.
2. Net inside the expense: `n_p = paid_p − owed_p`. A person's own share is covered by their own
   contribution first (self-pairs never exist). Creditors have `n > 0`, debtors `n < 0`, and
   `P = Σ n⁺ = Σ |n⁻|`.
3. Proportional: debtor `d` owes creditor `c` `floor(|n_d| × n_c / P)` (`BigInteger`; operands
   can reach 1e24).
4. Leftover minor units: each debtor row and creditor column is short by fewer units than the
   number of counterparties. Fill those residuals in one pass, debtors ascending by UUID,
   creditors with the **primary payer first** then ascending UUID (north-west corner rule). Both
   margins are then exact; no unit is created or lost.

Properties (tested): every debtor's row sums to `|n_d|`, every creditor's column to `n_c`; a
single-payer expense reduces to "each other participant owes the payer their share", identical
to the existing SQL; pairwise sums reconcile with net balances; output is independent of input
order.

Implementation: single-contributor expenses keep the existing aggregate pair query (filtered to
one contribution). Multi-contributor expenses are loaded with two batched queries (their
contributions and shares) and attributed in Java (`ContributionAttribution`). Multi-payer entries
are expected to be a small minority, so this keeps the "fixed number of queries" rule. Simplified
mode is unchanged: it nets canonical balances.

## Rounding

- Share rounding is unchanged: strategies floor and the payer (now the primary payer) absorbs the
  remainder.
- Attribution rounding: the primary payer receives leftover units first (step 4).
- Contributions are entered exactly; there is no contribution rounding.

## Lifecycle, history and neighbours

- Edit/delete/restore require every old contributor (not just `paid_by`) and every old share
  participant to be active, else the existing 409 re-add guidance.
- Duplicate aliases of one owner among new contributors are rejected like shares; historical
  duplicates may be retained.
- Revisions and create receipts carry `contributions` from now on. Pre-E03 snapshots do not.
- Refunds (B01, not owned this wave) keep crediting `paid_by`, i.e. the primary payer receives
  the refund. Zero-sum holds. A per-contributor refund split is a follow-up if wanted.
- Dashboard (not owned): totals/people/settlements come from the owned balance/projection
  services and are correct. The activity feed's per-item `viewerDeltaMinor` still treats the
  primary payer as paying everything for multi-payer items; the dashboard owner (H03, Wave 7)
  switches it to the contribution query this slice adds for the expense list.
- H05 CSV "paid" column: switch to contributions after H05 merges and this branch rebases.
