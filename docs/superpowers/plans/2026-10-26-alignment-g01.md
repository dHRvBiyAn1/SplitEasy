## Identity and migration

- Add `participants`, `participant_account_links`, `group_participants` and `group_invitations`. V17 follows integrated V16; preserve all older migration files.
- Backfill each existing account's primary financial participant with exactly the existing user UUID, name and creation date. Add a PRIMARY ownership link. A participant has one owner for life; an account can own several participants. A PRIMARY link has participant ID equal to account ID. Guest IDs are independent UUIDs permanently scoped to their creation group, including after a claim.
- Ownership links are append-only. No account merging, reassignment or unlink feature ships in G01. Claim preview/confirmation explains the consequence and that it cannot be undone here.
- Backfill active financial-roster rows from current memberships. Backfill inactive rows for every other expense payer/share/payment payer/payee referenced in each group, including deleted expenses. Preserve former-participant eligibility and account-only behavior.
- Change only four monetary FK targets to participants: `expenses.paid_by`, `expense_participants.user_id`, `payments.payer_id`, `payments.payee_id`. Keep existing column names/UUID values and all currency, amount, share, split, operation, version, deletion and timestamp values unchanged.
- Keep creator, authenticated recorder, membership, receipt actor, challenge and session FKs on accounts. Dashboard activity's existing actor means financial payer; expense revision actor means authenticated recorder. Give financial roles a separate ParticipantSummary type instead of weakening the account UserSummary type.
- Preserve `expense_revisions` JSON and `create_operations` intent/response JSON byte-for-byte as stored. Historical IDs/split inputs remain original. Read adapters may add clearly current identity metadata without replacing original identities or historical facts. Original receipt recovery uses the original submitted IDs, never their current canonical replacements.
- Registration atomically creates the primary participant/link before its session is issued. New groups create both creator membership and primary financial-roster eligibility. Live primary display data comes from the current account; guest labels remain durable facts.
- Group deletion retains its existing cascade policy: group-scoped guests, invitations and their ownership links can disappear with their group's financial history. Primary participant identities survive. Account closure remains A04; never cascade account deletion through shared financial facts.

## Projection and financial lifecycle

Resolve participant ownership and roster in one shared financial-identity module. A linked participant's canonical identity is its account's primary participant; an unclaimed guest is its own canonical identity. Use coherent read snapshots and batch lookups.

Map original identities to canonical identities **before** summing net balances or netting direct pairs. Drop canonical self-pairs, net reciprocal obligations independently by currency, and feed canonical net rows into existing simplification. Raw direct obligations are unsimplified obligations after ownership resolution; original identity-level facts remain in expense/payment history. People, pairwise, settlements, net totals, departure and mode-change checks use this same interpretation.

Example: existing account A owes C USD200 and guest G owes C USD300. A explicitly claims G; original rows remain unchanged and A owes C USD500 once. An old A→G payment stays history but no longer creates an external self-obligation. New payments between identities owned by the same account fail. Check keyed payment replay before new-write eligibility so a valid old self-after-claim payment still returns its original receipt.

Viewer deltas gather shares from **all** owned participant IDs and sum by expense; any owned payer counts as the viewer's paid contribution. Replace the existing one-share-per-account assumptions in expense/activity reads. Preserve all C01 currencies, precision, safe integer rules and settled/payment-only denomination rows.

Membership continues to grant account access only. Guest creation adds financial eligibility, never a login or membership. Accepting an invitation ensures one membership plus active primary roster; claiming a guest adds ownership without duplicating financial entries or membership. Leaving/removing a linked member checks combined canonical net/obligations and deactivates all of that account's group aliases. Re-adding the registered account reactivates its retained group aliases so historical edit/delete/restore remains possible. Guest roster removal has the same per-currency settlement guard but grants/revokes no account access. Creator protections stay account-based.

Lifecycle refinement: retained unclaimed guests need an explicit way back onto the financial roster, otherwise H01's re-add-before-correction/restore guidance becomes impossible for them. GroupResponse also exposes `inactiveGuests`; `POST /groups/{g}/participants/{p}/reactivate` restores the same scoped unclaimed identity and label without creating another identity or changing money. Claimed aliases use account re-add instead. Removing a guest revokes its outstanding targeted invitations; later reactivation does not revive those tokens. A fresh invitation is required. This closes the remove/re-add/recovery loop and prevents a previously issued invitation from undoing the removal.

New expense defaults select one canonical active person. Reject duplicate aliases of one owner in a new submitted split with explicit review guidance; never silently redistribute original inputs. A historical expense can retain its original distinct aliases after claim, including both identities in one split. Updates may retain those original duplicate-owned rows, but may not introduce additional duplicate aliases. Preserve original typed inputs, rounding identities, shares and expense versions until an explicit accepted edit. Restore retains original IDs and requires current eligibility of each original participant.

## Wire compatibility and retries

Use `X-Participant-Version: 1` independently of `X-Ledger-Version: 2`; CORS and the Angular API adapter include both. Existing financial request names such as `paidByUserId`, `participantUserIds`, `splits[].userId`, `payerUserId` and `payeeUserId` remain documented compatibility aliases for **financial participant IDs**, with the stable existing UUID mapping. Do not infer identity domain from UUID shape or silently canonicalize request fingerprints.

Financial ParticipantSummary retains compatible `id`, `displayName`, nullable `email`, plus current `canonicalParticipantId` and nullable `accountId`. Guest invitation targets are private delivery metadata, not a financial summary email. Auth/profile/creator/member/recorder UserSummary still denotes an actual account with its existing contract. Old snapshots can lack new metadata; they remain usable historical facts, not proof of current ownership.

GroupResponse keeps `members` as access accounts and adds canonical active `participants`, `viewerParticipantId` and the viewer's owned participant IDs. New defaults and settlement use these explicit financial identities. Historical edit forms retain original alias rows from expense detail even when the current default roster is deduplicated. Creator/leave routes use account IDs; guest-roster controls use participant IDs. Do not overload member counts or auth IDs.

Without the participant capability, retain existing account-only behavior. A group with any guest/alias identity requires capability before incompatible reads or new mutations, after normal authorization. Dashboard must return upgrade guidance rather than silently omit such groups. Cover group/roster, active/deleted/history, all balance/projection/payment endpoints and combined group mutations; prevent a write before an incompatible response is rejected. An unsupported old client must never apply a partial mutation.

Authorize exact keyed receipt recovery before new-write eligibility/capability checks. A representable original account-only receipt can be recovered even if the group later gained guests; this performs no new write. Incompatible guest receipts still require the capability. Preserve currency receipt enrichment and exact original payload identity. Do not rewrite old JSON to fit new DTOs or use a live resource to rebuild a deleted/edited receipt.

Retain existing immediate `POST /groups/{g}/members` for registered-account compatibility and explicit historical re-add; it never discovers or claims a guest by matching email. This deliberately preserves the existing contract and fixtures rather than silently changing a successful200 into an invitation202. New guest/email invitation UI uses separate commands and accurately distinguishes pending invitations from membership. Whole-scope capability checks still apply in guest/alias groups. Native links and this legacy account command never attach guest debt.

Owned uncertain drafts retain their original field family, IDs, currency and operation ID through migration/claim. Detect legacy/new draft shape explicitly; do not guess by UUID or relabel by preferences. Payment original retries dispatch the saved payload rather than reconstructing identities from a new settlement projection. Changed intent requires explicit acknowledgement. A never-committed draft whose selected aliases now share an owner gets actionable review instead of a silent rewrite.

## Invitation commands and consent

New routes require the participant capability and A03 authentication:

| Command | Contract |
| --- | --- |
| `POST /groups/{g}/participants` | Create a named group-scoped guest; optional operation identity prevents duplicate retry creation. No account/mailbox lookup. |
| `DELETE /groups/{g}/participants/{p}` | Deactivate a settled unclaimed guest's financial eligibility; preserve facts. Account removal stays the membership route. |
| `POST /groups/{g}/participants/{p}/reactivate` | Explicitly re-add the same retained unclaimed guest for historical correction/recovery; no new identity or automatic invitation. |
| `GET /groups/{g}/invitations` | Current-member status metadata; no raw tokens. |
| `POST /groups/{g}/invitations/email` | Send to normalized validated email, optionally targeting an exact unclaimed guest. Optional operation identity deduplicates accepted send commands. |
| `POST /groups/{g}/invitations/links` | Create an explicitly single-use, expiring join link; plaintext URL returned once for deliberate copying. |
| `DELETE /groups/{g}/invitations/{i}` | Revoke a pending invitation; an accepted claim is not undone. |
| `POST /invitations/preview` | Body token; bounded read-only invitation/claim review under the authenticated account. |
| `POST /invitations/accept` | Body token and explicit confirmation; atomically claim/join once. |

Tokens use independent 32-byte SecureRandom values and SHA-256 hashes at rest. Default lifetime is24h. Validate purpose, pending state, expiry, revocation, exact guest scope and current account after lock waits. Invalid/consumed/expired/revoked tokens produce sanitized unavailable guidance, with no group/account directory disclosure.

EMAIL acceptance requires current persisted `emailVerified=true` and normalized current email equal to the invitation target. Reuse A02 verification separately. No claims on registration, login, phone, display-name match, mailbox lookup or group-link acceptance. Preview shows guest liabilities only to the verified recipient, along with that account's existing and resulting per-currency balances and an explicit irreversible-ownership explanation. A claim requires explicit ownership confirmation; ordinary membership acceptance still requires an explicit Join action. Balances can change as group entries change; show the review snapshot without promising a locked financial quote.

LINK acceptance requires an active authenticated account and joins only its primary identity. It does not require email ownership to claim a guest because it never claims one. Forwarding transfers the remaining join opportunity, which creation UI explains. Reused link acceptance fails; revocation/expiry invalidates it. Never store plaintext links in retry receipts or logs. If creation response is lost, metadata can identify/revoke the unknown link; deliberate replacement yields a new secret. Show honest uncertainty, not automatic generation or recovered plaintext.

Email issuance reuses native SMTP sender/TLS/HTTPS/egress validation. Disabled/misconfigured/failed delivery is actionable503 and does not pretend an invitation was sent. Guest creation and group-link generation remain usable independently. Issuance persists metadata-only operation receipts; an exact retry sends no second email. Explicit resend rotates/revokes old tokens. SMTP can deliver before a later transaction rollback; an orphan delivered token fails, with no promise of exactly-once external delivery or a new outbox. Keep bounded existing-pattern process-local rate limits for issuance and token preview/acceptance. Token, target and guest financial facts stay out of logs.

Invitation pages capture/scrub fragment secrets immediately, hold them only in memory, and require explicit preview/acceptance. Use the simple **sign in/register/verify, then reopen the original invitation** flow; no duplicate inline auth UI or token-bearing return URL/storage. Clear secret/preview on destruction or session replacement. Same-route fragment reentry follows the A02 protections. Never accept on navigation, login, verification, preview or reload. Scope every callback to immutable account/session/route ownership.

After an uncertain acceptance response, disable another acceptance and offer explicit status reads. Membership alone cannot prove a guest claim if the account was already a member: check the original guest against the current owned participant IDs as well. A hard reload requires reopening the original link; there is no automatic POST recovery.

## Transactions and races

Normal guest/roster/invitation mutations use READ_COMMITTED and the existing group lock with membership recheck after waiting. Acceptance resolves only a candidate group ID from a strict token hash, locks that group, then locks the current account, then rereads invitation/guest/ownership and actual wall-clock expiry. A valid capability authorizes only this join/claim module; there is no general group-authorization bypass.

All accept/revoke/resend/group-delete/financial paths acquire group before account/participant/invitation locks; A02 account operations acquire account rows only. Never preload a stale managed account before waiting for its lock. DB uniqueness owns one participant owner and one group membership. Commit ownership, membership/roster and invitation consumption together. Guest group scope keeps the affected projection inside one group lock. Concurrent claims, claim/revoke/resend/delete, changed verified email, membership removal and financial writes must have coherent one-winner outcomes without changed money or snapshots.
