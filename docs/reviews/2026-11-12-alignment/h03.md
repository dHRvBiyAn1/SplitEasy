# H03 — durable activity and in-app notifications (2026-11-12)

Plan: `docs/superpowers/plans/2026-11-12-alignment-wave7.md` (H03). Migration V25. In-app only.

## What shipped

- V25: `activity_events` (identity `seq`, `idx_activity_events_group_seq`), `notifications`
  (unique event+recipient), `notification_preferences` (absent row = all true). No backfill.
- `activity.ActivityRecorder`, called from `ExpenseHistory.record`, `LedgerHistory.record` and
  `GroupService` (archive, unarchive, delete, restore, member added/removed/left). No expense,
  payment, refund or dashboard service was edited. Payment/refund group ids are read by SQL in the
  same transaction because the generic `LedgerHistory.record` signature carries no group.
- Read: `GET /api/activity`, `GET /api/notifications`, `/unread-count`, `POST /{id}/read`,
  `/read-all`, `GET/PUT /api/me/notification-preferences` (OpenAPI under the h03 anchors).
- Frontend: `/activity` and `/notifications` routes, shell bell + Activity link, lazy-loaded
  notification switches in Profile (a `<details>`; it loads on first expand so opening Profile adds
  no request).

## Red → green

- Backend `ActivityNotificationIntegrationTest` (6 cases): red first (endpoints 404, no table), green
  after V25 + recorder. The first green run caught my wrong expectation that expense edits are
  `CORRECTED`; the real revision action is `REPLACED`, so the event kind is `EXPENSE_REPLACED`.
- Frontend: 4 rendered specs (activity paging/filter/retry, mark-read/all, failed mark-read,
  preferences save + failure). Adding the bell made existing specs that render the shell fail on an
  unexpected `/api/notifications/unread-count`; `app.spec`, `overview-read-retries.spec` and
  `session-isolation.spec` now provide a no-op `NotificationService`.

Convention / data-model lines:

- **Activity events**: write only through `ActivityRecorder` inside the financial or group transaction; kinds are `EXPENSE_|PAYMENT_|REFUND_` + revision action (`CREATED/REPLACED/DELETED/RESTORED`), `GROUP_*`, `MEMBER_*`. Recipients = current members except the actor, filtered by `notification_preferences`.
- **Data model**: V25 `activity_events(id, seq identity, group_id→groups cascade, kind, subject_id, actor jsonb, summary jsonb, occurred_at)`, `notifications(id, recipient_id, event_id, read_at, created_at; unique event+recipient)`, `notification_preferences(user_id, expenses, payments, group_changes)`.
- **Frontend**: `NotificationService.unread` is the bell owner, revalidated on navigation/visible focus and cleared on session change. Specs that render `App` provide a stub for it.
