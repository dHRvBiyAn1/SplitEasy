## Decisions the plan left open

- Runner takes the **group row lock first, then the schedule row lock** (ExpenseService locks the group too), and the
  service locks group then schedule, so there is no lock-order deadlock. Two runners serialise per group.
- A failure (creator left, group archived/deleted, inactive payer/participant, bad template) is detected from
  `ExpenseService.createExpense`'s own Forbidden/NotFound/Conflict/BadRequest; that attempt rolls back (no partial
  expense), then a second transaction records the occurrence `FAILED` and sets `NEEDS_REVIEW` with the message.
  `next_date` moves past the failed date, so editing resumes from the next occurrence, not the failed one.
- Catch-up: a date is generated if it is at most 30 days before today (inclusive, so 31 dates on a daily
  schedule); older dates are `SKIPPED`. The cap of 31 counts created expenses only (SKIPPED are cheap inserts).
- PUT sets `next_date` to the first anchored occurrence on or after today in the schedule zone.
- Cancel is idempotent (second call returns the cancelled schedule) and works on archived groups. Create/PUT are 409
  on archived groups.
- Reminder reads the canonical projection (`ObligationProjectionService.forGroup`) outside any transaction (it owns
  REPEATABLE_READ), then dedups under `pg_advisory_xact_lock`. 409 when nothing is owed or one was sent in 24 h.

## Review follow-up (integrator, PR #124)

1. **Create retry identity.** V28 gains `operation_id` + `uq_recurring_schedules_operation (created_by, group_id,
   operation_id) WHERE operation_id IS NOT NULL`. Create looks up a replay first (identical intent returns the
   original schedule, changed intent 409), else inserts `ON CONFLICT ... DO NOTHING` and re-reads on conflict.
   Frontend: `PendingWritesService` kind `recurring` (flat expense checks skipped, like `group`); one operationId for an
   identical uncertain draft, a changed draft abandons and mints a new one, success/session reset clears it.
2. **Template validation** at create and edit: a dry run of `ExpenseService.createExpense` that rolls back (its own
   transaction, run before the write takes the group lock), so payer/contributor/participant eligibility and split
   math use the real path; 400 in the expense message style, no expense or event is left behind.
3. `describeEvent` handles `BALANCE_REMINDER` ("Alice reminded you about USD 12.00 in Trip"); rendered specs for the feed
   and the bell list.
