## What actually exists

Routes are login, register, dashboard, group detail, group settings and profile. `/groups` redirects to dashboard; unknown routes redirect there too. Dashboard activity and People are sections, not separate pages. Group detail lists expenses; there is no group activity tab or dedicated payment-history screen. The payments history API exists. Add member is reached from settings in this baseline. Global modals are New group, New/edit expense, Settle up, and Add member.

The existing visual system uses Instrument Serif, Hanken Grotesk, lime, sharp application surfaces, green/pink financial states and circular avatars. Some auth presentation uses rounded surfaces. Both light and dark themes exist. There are already CSS entrances, modal scale/fades, hover effects and reduced-motion overrides; this is not a motion-free app.

## Before / after priorities

| Before | Proposed after | Why |
|---|---|---|
| Mobile account navigation disappears | Persistent account access plus group drawer/bottom navigation | Every current route/action remains reachable by thumb and keyboard |
| Anonymous modal; focus stays behind it | Named dialog, managed initial focus, inert background, contained Tab, restored launcher | A dramatic modal must remain usable |
| Repeated full financial mini-dashboard per group | One clear group net + total-spent context; details on demand | More visual character with less financial noise |
| Chips for every group/category/payer simultaneously | Compact scope selector, clear payer control, category picker | Reduces scanning/scroll burden without removing options |
| Bare alerts / silent failure / close-on-success | Field errors, retry states, partial success and lightweight receipt feedback | Finish the experience beyond its ideal state |
| Inconsistent large/small number formatting | One cents-based display primitive, signed net semantics, tabular numerals | Keep digits and direction trustworthy |
| Whole-view fade-up and 160ms modal entrance | Cause-and-effect motion: pass→ledger, split allocation, receipt→success | Memorable motion tied to what the product does |

## Coverage limits

This is a complete **source inventory** and broad **browser sampling**, not an exhaustive visual test matrix. Fresh captures cover the screens/states listed above. Loading is observed transiently in browser state and source; deliberately delayed requests, every 4xx/5xx variant, save-under-network-loss, all mutation combinations, register/login invalid server responses, actual screen-reader output, every responsive breakpoint and real-device Safari were not all freshly exercised. No production fault injection or production performance testing was performed. Reduced-motion behavior was source-inspected; a complete OS-level reduced-motion browser run is an implementation acceptance requirement. Profile persistence bugs and ledger protections are not claimed fixed by a proposal.
