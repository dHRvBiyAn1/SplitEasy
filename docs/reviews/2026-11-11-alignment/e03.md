## Behavior and scope

Money actually paid is now stored per financial participant in `expense_contributions`, separate
from what each participant owes (`expense_participants.share_cents`). V23 backfills one row per
existing expense from `paid_by`/`amount_cents`, deleted rows included, so restored expenses still
read. `expenses.paid_by` is unchanged and means the **primary payer**: a named contributor and the
rounding recipient.

`CreateExpenseRequest.contributions` is optional. Absent/null keeps the exact single-payer
contract; present, it must be nonempty, duplicate-free, name active financial participants,
include `paidByUserId` and sum exactly to the amount (400 before any row changes). It is omitted
from the normalized retry intent when null, so pre-E03 keyed claims stay byte-identical and
replay normally. `ExpenseResponse.contributions` is always present on current reads;
`ExpenseSummary` gains `payerCount` and its `viewerDeltaMinor` becomes owned contributions minus
owned shares.

A full-replace PUT without contributions on an expense with several payers returns 409 with
reload guidance, mirroring the legacy-currency guard: an old client must not silently collapse
several payers into one. PUT with contributions replaces both sides atomically. Edit/delete/
restore now require every old contributor (not only `paid_by`) plus every share participant to be
active, otherwise the existing re-add 409.

Net balances read paid amounts from the contribution aggregate. Direct obligations keep the
existing single-payer SQL and attribute multi-payer expenses in Java
(`ContributionAttribution`): per-expense canonical net, proportional floor, then a debtor-UUID /
creditor-UUID north-west-corner pass that fills residuals primary-payer-first, so every debtor row
and creditor column is exact and nothing is created or lost. Simplified mode is untouched (it
nets canonical balances).

Also switched after G02.2/H05 merged (merge of `origin/dev` 344bc88, no conflicts): the dashboard
activity feed's `viewerDeltaMinor` (batched contribution read, no N+1) and the history CSV
`paid_minor` / friend-scope parties read contributions. Not changed: refunds still credit the
primary payer (B01).

## Migration and rollout

- `V23__expense_contributions.sql` is additive: new table, unique `(expense_id, participant_id)`
  (leftmost prefix serves the expense FK), index on `participant_id`, CHECK `amount_cents > 0`.
  Backfill inserts `(paid_by, amount_cents)` for every expense.
- Drain old backends before V23. An old binary inserts an expense without a contribution row and
  readers take paid amounts from the table, so that expense's payer would vanish from balances.
  Rollback before any multi-payer write is schema-compatible (old code ignores the table); after
  a multi-payer write an old binary treats the primary payer as having paid everything — still
  zero-sum but wrong — so rollback is a forward fix.
- No change to expenses, shares, split intent, versions, deletion markers, revision JSON or
  create-operation JSON. Pre-E03 snapshots and receipts simply lack `contributions`.
