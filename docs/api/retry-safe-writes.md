# Retry-safe creates and expense versions

Group and expense POST accept optional UUID `operationId`. Keys are scoped by the authenticated actor, resource kind and group; group creation uses the actor as its scope. IDs carry no authorization. Every expense attempt reauthorizes current group membership before claim/replay; group replay requires membership in the original group. An identical intent returns the original 201 response, including original fields/timestamp even if the resource was later edited or deleted. Changed intent with the same key returns 409. Failed transactions reserve nothing. Missing/null IDs retain legacy additive behavior.

V12 claims operations and stores normalized submitted intent plus immutable response snapshots in the same transaction as the create. Native PostgreSQL `ON CONFLICT DO NOTHING` and a READ COMMITTED lookup handle concurrent claims without catching a uniqueness exception in an aborted transaction. Intent normalizes trimmed descriptions/names, default types/categories and participant ordering; an omitted expense date remains omitted in the fingerprint so retrying tomorrow still returns yesterday's result. Operation records deliberately survive resource deletion; no automatic expiry is supported. Account deletion cascades its claims. These records are response snapshots, not a financial audit log.

Expense detail and list responses expose nonnegative `version`. New clients submit that version as `expectedVersion` in PUT JSON or as DELETE query parameter. Under the existing group row lock, explicit mismatches return 409 before mutation. Every accepted PUT immediately advances the parent version, including child-only split intent changes and no-op replacements; the response contains the flushed current opaque token. It is not an edit counter. Invalid or rejected edits roll back without advancing the visible version. No stale edit is automatically retried; reload and review the winner while preserving the draft. Former-participant guards and current membership checks still apply. Group settings PATCH remains dirty-column/last-write-wins; its disjoint-field behavior is unchanged.

Missing expected versions are accepted only before `app.expenses.version-required-from` (default `2026-11-19T00:00:00Z`, configurable via `APP_EXPENSES_VERSION_REQUIRED_FROM`). At and after the UTC instant they return 400 with upgrade/reload guidance. Configure a finite promotion deadline, deploy V12/server first, deploy the version-aware frontend, check deployed clients before the deadline, and record any explicit finite extension. There is no disable switch. Explicit mismatches are rejected throughout compatibility. The configured cutoff is checked using a UTC Clock and the exact boundary is exercised over HTTP.

Browser pending intent and operation IDs are stored in account-owned, tab-isolated sessionStorage before dispatch. Reload/reopen restores uncertain drafts; it never sends automatically. Explicit identical retries reuse their ID. Network/server/conflict failure preserves the original identity. A changed draft cannot silently allocate another ID: explicitly abandon the uncertain operation, acknowledge that it may already have succeeded, then start the separate intent. Check history before abandoning. Success removes only its own matching identity; session reset removes this tab's pending records and cancels old requests. Another tab cannot overwrite or clear these records. A new tab without a copied draft has no retry identity; check history before recreating an uncertain write there. This is neither offline support nor a durable dispatch queue. Browser storage failure blocks the write with actionable feedback.

Rollback: V12 is additive and V1–V11 are immutable. Deploy V12 before or together with A02 V13; never promote V13 alone first. Do not run old and new backend writers concurrently: old writers do not increment versions, so mixed backend fleets defeat stale-edit protection. Legacy clients are compatible only against the new server, which advances versions even when expectedVersion is omitted. Replace the single backend coherently and verify its version before enabling clients. An old binary may read additive schema but bypasses expected-version checks and does not advance resource versions, so restoring one after version-aware writes requires a forward fix or reviewed maintenance/data recovery procedure. Do not drop claims or reset versions to roll back: that would make retries duplicate and stale clients valid again. WEIGHTS/ADJUSTMENTS retain the separate V11 rollback ceiling.

C01 adds explicit currency/minor units without rewriting stored receipts. Old USD snapshots are enriched only from their own historical values; missing currency meansUSD, never a profile preference. All original IDs/versions/amounts/intent survive edit/deletion.
