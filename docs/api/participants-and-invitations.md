# Financial participants and group invitations

G01 keeps a lasting financial participant separate from a sign-in account and account membership. Existing accounts retain exactly the same UUID as their primary participant. Unregistered people have separate group-scoped UUIDs. Several immutable participants can belong to one verified account; the account remains the actor that owns sessions, group access and retry operation keys.

Expense `paidByUserId`, `participantUserIds`, `splits[].userId`, payment `payerUserId`/`payeeUserId`, and financial summaries' `id` remain compatibility field names for **financial participant IDs**. They do not become account IDs when someone claims a guest. Auth/profile, group creator/members and revision recorder summaries still refer to actual accounts.

## Current financial identity

ParticipantSummary has `id`, nullable `email`, `displayName`, current `canonicalParticipantId`, and nullable `accountId`. An unclaimed guest's email is null; the addressed invitation mailbox is private delivery metadata. Scoped guest labels remain available in original history and edit rows. Canonical balances and the default roster use the current account's name after a claim.

GroupResponse retains account `members` and adds canonical active `participants`, `viewerParticipantId`, that group's retained `ownedParticipantIds`, and `inactiveGuests` for scoped unclaimed inactive people. DashboardResponse adds the viewer's primary `viewerParticipantId` and all `ownedParticipantIds`. Ownership metadata grants no group access. Old immutable receipt/revision snapshots may lack current identity metadata or preserve metadata as it was recorded; use the authorized current group mapping to interpret current ownership.

Derived balances sum all aliases per person and currency. Direct obligations map both original endpoints before reciprocal netting and remove self-pairs; simplification consumes those canonical nets. Original expense/payment rows, typed inputs, rounding identities, versions and immutable snapshots remain unchanged by claiming. Thus account A owing C USD200 and guest G owing C USD300 become one USD500 obligation when A explicitly claims G. A recorded A→G payment remains historical fact but no longer creates an external obligation.

New expense defaults select each canonical active person once. Selecting duplicate owned aliases for a new split fails 409 with review guidance. Historical edits can retain the original distinct aliases, but cannot introduce additional duplicate-owned rows. New payments between aliases of one owner fail 400; an exact previously accepted keyed payment is recovered before this new-write eligibility check.

Account removal/leave requires zero canonical net in every currency and no current-mode obligation, removes access, and deactivates every group roster alias owned by that account. Registered-account re-add restores retained aliases so old expense edit/delete/restore eligibility is explicit. Creator protections remain account-based. Settled unclaimed guests can have financial eligibility deactivated separately; removal revokes their outstanding targeted invitations. `inactiveGuests` makes the same retained identities discoverable for explicit reactivation. Reactivation preserves the original ID/label, changes no money, and never revives an old token; claiming remains separate and a fresh invitation is required. Historical facts remain and former financial participation grants no access.

## Capability and original retries

Send `X-Participant-Version: 1` independently of `X-Ledger-Version: 2`. Missing/other participant markers retain account-only compatibility. Any guest/alias in a scope, including retained inactive/deleted-history identities, requires the marker before incompatible group/financial reads or new mutations. Dashboard fails as a whole rather than omitting affected groups. Authorization still precedes capability errors. New participant/invitation commands always require 1.

Recover an already-accepted exact keyed group/expense/payment receipt after current membership authorization and before checking new-write eligibility. A representable original account-only receipt remains recoverable after the group gains guests; a guest/alias receipt requires capability. Receipts use original IDs and original stored responses even after edits/deletion/claim. Changing identity, money or other fingerprinted intent with the same operation ID remains409. Never reconstruct a pending payment from the latest settlement projection or canonicalize its original payer/payee IDs.

The existing immediate `POST /groups/{g}/members` still adds registered accounts and performs explicit historical re-add; it never discovers or claims a guest from matching email. Guest/email invitations use separate commands and remain pending until accepted. See [OpenAPI](../../openapi.yaml) for exact DTOs and errors.

## Invitations

- `POST /groups/{g}/participants` creates a named guest with optional `operationId`, no account/mailbox lookup. It grants financial eligibility only. `DELETE /groups/{g}/participants/{p}` deactivates a settled unclaimed guest and revokes outstanding targeted invitations. `POST /groups/{g}/participants/{p}/reactivate` returns 200 ParticipantSummary for the same retained unclaimed identity, without a request body or new identity. Claimed aliases use account re-add.
- `POST /groups/{g}/invitations/email` takes `email`, optional exact unclaimed `participantId`, optional `operationId`, and optional `resend`. Same pending target deduplicates. Explicit resend rotates/revokes all pending invitations for that guest, including a changed recipient; choosing a different recipient without explicit resend conflicts. Exact accepted issuance retries return metadata without another delivery.
- `POST /groups/{g}/invitations/links` returns `{invitation, url}`. Resolve its relative URL against the frontend origin. This is an explicitly single-use, expiring, revocable Join link, independent of SMTP. The secret is returned once and is absent from status/retry records. Forwarding transfers the remaining Join opportunity, but never claims an existing guest, even with a matching name or email.
- `GET /groups/{g}/invitations` returns metadata statuses only. `DELETE /groups/{g}/invitations/{i}` revokes a pending invitation. Revocation cannot undo an accepted ownership claim or membership.
- `POST /invitations/preview` accepts `{token}` under the current account and reads a review without consuming it. A targeted EMAIL recipient must have a current verified matching mailbox before guest liabilities are disclosed. The review includes existing, guest and resulting per-currency net amounts and the irreversible ownership consequence. It is a snapshot, not a locked quote. These are net positions; zero net can still have offsetting direct obligations.
- `POST /invitations/accept` accepts `{token, confirmOwnership:true}` for a targeted guest. Ordinary membership/Join acceptance uses an explicit POST and can omit `confirmOwnership`. The result is `{groupId, participantId, accountId, claimed}`. Guessed, wrong-purpose, consumed, expired, revoked and wrong-account tokens fail 400 with sanitized unavailable guidance. Concurrent acceptance has one winner; a second accept fails rather than duplicating access or money.

Default invitation lifetime is 24h. Tokens are independent 32-byte SecureRandom values, encoded as 43-character base64url and stored only as SHA-256 hashes. Issuance allows 30/account/hour, 100/IP/hour and 100/group/hour; preview/acceptance allow 30/account/5min and 100/IP/5min. These are bounded process-local limits with 429 Retry-After. Share enforcement before multiple instances. Email verification/reset/change tokens are separate purposes and cannot be substituted.

## Browser and delivery security

Invitation URLs put action/token in the fragment. Capture and scrub immediately; hold secrets in memory only. Sign in/register/verify, then reopen the **original invitation** and explicitly review/accept under the displayed account. No secret return URL, browser storage, persisted draft or automatic acceptance on preview/navigation/login/reload is supported. Session/route replacement clears the secret and cancels stale callbacks. After an uncertain acceptance, offer an explicit authorized status/group read; membership alone does not prove a guest claim when the account was already a member, so check the original guest against current owned IDs too.

Native SMTP reuses configured sender/TLS/HTTPS/egress validation. Disabled, misconfigured or failed delivery returns actionable 503 with no committed invitation or false “sent” state. Tests/local mailbox can enable delivery; production SMTP remains explicitly deferred. SMTP can deliver before a later transaction rollback, leaving an invalid orphan link; G01 does not promise exactly-once external delivery or introduce H03's future outbox. Phone remains unverified contact preference; phone/SMS invitations require a selected verified channel and do not ship here.

Acceptance reads only a candidate group ID from a strict token hash, locks the group, then locks the current account before rereading invitation/ownership/verified email and actual-clock expiry. It also rechecks JWT expiry/credential version and persisted active device/session deadlines after waiting. Claim, membership/roster and token consumption commit together. Revoke/resend/delete/financial writes serialize on the group; no account-lock-first path acquires a group lock. A pending capability authorizes only this invitation module, with no general group guard bypass.

## Migration and rollback

V17 follows V16. Backfill every account's primary participant using its exact existing UUID/name/date and add its PRIMARY ownership link. Backfill active roster from memberships and retained inactive roster from every expense/share/payment reference, including soft-deleted expenses. Change only the four monetary FK targets to participants; column names and values remain unchanged. Creator, recorder, membership, receipt actor, challenges and sessions remain account references.

Do not rewrite amounts/currencies/shares/split inputs, IDs, versions/deletion timestamps, expense-revision JSON or create-operation intent/response JSON. Registration creates primary participant/link atomically before session issuance; a new group creates both access membership and financial eligibility. Group deletion retains the existing financial cascade, including its scoped guests/invitations; primary account identities survive. Account closure/retention remains A04.

Drain all old application instances before this schema/application accepts traffic. Old readers join financial roles to accounts and omit guests; old writers omit participant/roster maintenance. After guest or alias data exists, keep this schema and use a compatible forward fix rather than an old binary. Rehearse V16→V17 on populated disposable data and compare original monetary IDs/values plus stored revision/receipt JSON hashes. Deployment and production promotion remain separately authorized gates.
